### Fixed

- `buffon up` builds the dashboard. It wrote `up.json` into `<home>/site` before running `buffon dashboard --out <home>/site`, which refuses a non-empty directory it did not write, so every `up` ended on the fallback summary page ("the dashboard did not build ... is not empty"); and had it run, it would have replaced the report built into the same directory. The directory `up` rebuilt on an earlier run is now cleared, the dashboard is built into it, the report is built beside it and moved to `site/report` afterwards, and `up.json` and `build.log` are written last. The summary page remains the fallback for a dashboard that really fails.
- The cgroup meter on a host where the runner cannot join a systemd scope. `new_meter()` chose `cgroup-systemd` whenever `systemd-run --user --scope` made a scope with a writable `cgroup.procs`, but cgroup v2 also needs write access to the closest common ancestor of the runner's cgroup and the scope's. A runner under `system.slice` (a GitHub-hosted job: the user manager runs, the job does not live in it) failed every join with `PermissionError`, so every sample exited 127 and `buffon up` found no result. The meter now moves a probe process into the scope before it uses it; when that is refused it falls back to the `rusage` meter (recorded in each sample's `meter`) and remembers why: `BUFFON_METER=cgroup-systemd` (or `local.meter`) then fails with that reason instead of a `PermissionError` per sample. Run the benchmark inside `systemd-run --user --scope` (or set `BUFFON_CGROUP_ROOT` to a delegated cgroup) to get the cgroup meter. No published result is affected.

- The Pages site shows every published run. `tools/pages_site.py` built the dashboard over the newest run only, so the merge of the launch results replaced the full site with the last run's (PiG, Pi-Bolt, Start-up and Prompts and tools missing). It now builds over every run in `results/index.json` that is not withdrawn, and `.github/workflows/pages.yml` runs only by manual dispatch: the live site is served from the `gh-pages` branch, and a push to `main` no longer replaces it.
- macOS: on a host whose instruction counters the probe found unavailable (`perf.available` false), the process-tree meter still sampled `proc_pid_rusage` and reported `instructions` and `cycles` of 0 (`perf_scope` "sampled") for a short-lived child, which added zero-valued cells to the sample; it now samples counters only where the probe found them.
- `overhead/print-write` on GitHub Copilot CLI and Codex. Copilot's `create` tool requires the parent directory to exist ("Parent directories must exist before creating the file"), and the scripted call writes `big/source.ts`, so every sample failed with "the file was not written"; the workload now creates `big/` in the project first (the same for every harness, and the byte check is unchanged). Codex declares no write tool for the mock's model (an unknown model gets no `apply_patch`) and a built-in without a name (`web_search`), which made the skip message fail with `TypeError: sequence item 8: expected str instance, NoneType found`; the mock now names a built-in by its type, and Codex takes the write through its own `apply_patch` tool: a new `print_write` mode in `arms/codex/arm.toml` loads a model catalog (`model_catalog_json`) whose entry for the mock's model carries `apply_patch_tool_type = "freeform"`, and the mock answers with a patch in a Responses `custom_tool_call` (`write_call`, `patch_add_file`; the request's `custom_tool_call_output` ends the round). The file Codex makes ends with a newline (its patch format has no way to leave it out), and the check expects that. The manifest field `[modes] print_write` and the `{home}` placeholder in a mode's arguments are new.
- Codex's large-write catalog (`overhead/print-write`) now carries Codex's own instructions. The one-model catalog that turns on `apply_patch` for the mock's model held a one-line instructions text in place of the 17 KB text Codex sends on every other workload, so each Codex request in this test was about 17 KB smaller than in normal use. The text is now `arms/codex/base-instructions.md`, copied from Codex 0.162.1's own requests (NOTICE), and `arms.lock` hashes it. Results measured before it (every published run so far) keep their numbers; the site marks their Codex large-write cells with a measurement caveat.

### Changed

- Streaming: print mode is unpaced by default (`print_stream_rate_tps`, 0). The mock sends the answer as fast as the harness reads it, and a 60,000-character answer no longer waits 15 s for every harness. The TUI keeps its 1,000 tokens per second (`stream_rate_tps`), because chunk timing changes how a screen redraws. Each sample records the rate it used. A print-mode `wall_ms` is now the harness's own time, not the stream's length. Compare print-mode streaming only with runs that used the same rate.
- Campaign plans take `adaptive = true` on a family: its `buffon run` gets `--adaptive`, a cell stops once its answer is clear and `rounds` is the most it takes. The launch rerun's focus families are adaptive, and octet joins its core family. On a quiet benchmark host the plan takes about 2 to 2.5 hours instead of 3.5 to 4.
- **Renamed to Buffon**, after Buffon's needle (README, "Why Buffon"). The project was called pi-arena. The Python package `arena/` is `buffon/` and the command is `python3 -m buffon` (and `buffon.sh`, formerly `arena.sh`); the error prefix `arena:` is `buffon:`. Every `ARENA_*` environment variable is `BUFFON_*` with the same meaning (`ARENA_HOME`, `ARENA_SITE`, `ARENA_ACCEPT_TERMS`, `ARENA_CACHE_DIR`, `ARENA_CPUS`, `ARENA_MOCK_CPUS`, `ARENA_WORK_DIR`, `ARENA_SOURCE_REPO_*`, `ARENA_K8S_*`, `ARENA_CLUSTER_BIN`, and the rest); the old names are not read. The default home is `~/.local/share/buffon` (was `pi-arena`), the default cache `$XDG_CACHE_HOME/buffon`, and the host lock file `buffon.lock`, so an existing home or cache is not found under the old name: move it or set `BUFFON_HOME` and `cache_dir`. The Kubernetes helper binary is `buffon-cluster` (was `arena-cluster`), its Go module is `buffon/cluster`, the labels are `app.kubernetes.io/name=buffon` and `buffon/run`, the container is `buffon`, and the image path in a pod is `/opt/buffon`. The dashboard text, title and mark (a few needles across parallel lines) are Buffon's. The fields and keys of `raw.json`, `report.json` and `campaign.json` and the workload ids do not change; `kind` is `buffon-run` in new runs and the reader also accepts `arena-run`, so published runs still load. The `arms.lock` hash changes because the arms' notes name Buffon. The seed of the varied twins keeps the old name in its hash input so that every published seed still yields the same sessions.
- Site home: the headline says what Buffon measures instead of counting the harnesses, a short intro says how a number is made, and it links to How it works and to "Why Buffon". The README is carried as the About page (`#/doc/README`). The footer keeps its three links and drops the affiliation sentence.
- Statistics: adaptive stopping takes at least the rounds Holm across the compared arms needs (the smallest n with 2k / 2^n < 0.05: 6 rounds for one arm, 9 for eight, where it was a fixed 6), and a tight "no measurable difference" waits for the same minimum; `run.adaptive` records it. New: equivalence by TOST against the margins in `workloads/margins.toml` (CPU, instructions and wall time 5%; memory 5% or 2 MiB; bytes and tokens per turn exact), as `equivalence` in each `report.json` comparison and an `equivalent (TOST)` column in `report.md`; "no measurable difference" is a different claim and is unchanged (METHODOLOGY section 7). Fixed: macOS "peak memory, all processes" read near zero for a short command (one start-up cell came out 2121 times the reference) because the command exited before a `ps` sample landed; with no sample the value is now missing, and with one it is never below the largest process's `ru_maxrss`.
- The arena no longer sets GOMAXPROCS for any arm. It pins CPUs and leaves runtime tuning at each harness's shipped default, so PiG runs at its documented default (GOMAXPROCS unset) instead of being forced to the harness CPU count. A variable is set only by an arm's manifest `[env]`. Each arm's `runtime_settings` (what its manifest sets, and the known tuning variables left at the default) is recorded in raw.json and printed in the report. `Plan.parallelism` and the `parallelism` argument of `Harness` are removed.
- New `[[divergence]]` in arm.toml: where an arm does different work by its own account, the report shows its median and `different work: not compared (<reason>)` with no ratio, interval or test, and the grade leaves the cell out for that arm (`not_compared` in report.json and grade inputs, `arms[<id>].divergences` in raw.json). The Pi-Bolt arms declare it for `streaming/tui-*` (scroll regions). - Pi on Node is measured with a warm compile cache, as a person's second start is. A 7-harness run on the benchmark host hit the 1,024-descriptor limit after about 500 samples. The meter now closes its counters when it closes (`arena/runner/cgroup.py`); a test in `tests/test_perfcount.py` checks it.

- `arena run` and `arena calibrate` accept `--offline`, `--cache-dir` and `--npm-cache` on a local site (docs/RUNNING.md already said so); `arena campaign` on a local site passed them and the first real VPS run died on `unrecognized arguments`. - A pod's read-only root file system no longer stops a session: the host lock falls back from /run/lock and /var/tmp to the scratch directory named by TMPDIR (then the platform's temporary directory) and a lock that cannot be created says which file and how to move it (`ARENA_LOCK_FILE`); the first real cluster run failed with `OSError 30: /tmp/pi-arena.lock`. - The wall time of a short command no longer jumps from round to round. The meters waited for the exit with `wait4(WNOHANG)` and a 5 ms sleep (and `Popen.wait(timeout)` on the cgroup meter), so a 5 ms command read 12 to 42 ms while its CPU time stayed at 8 ms. The meters now wait on a pid file descriptor (Linux) or a kqueue process event (macOS) and stamp the exit when the kernel reports it (`arena/runner/exitwatch.py`); `Batch` and `Rpc` use that stamp for `t_exit`. The rusage of the whole tree and the timeout are unchanged, and a host with neither mechanism polls as before. In a Linux container `/bin/true` read 5.4 ms median before (0.2 or 5.5 ms per run) and 0.2 ms after, against 0.4 ms for a bare `subprocess.run`. Only start-up rows (`overhead/version`) were affected.

- A sample measures the harness from its exec to its exit, not the runner's start-up work before it. The runner forked itself, ran Python in the child (join the cgroup, pin, open the perf counters) and then exec'd, so the clock started before the fork, the cgroup and `wait4` counted the child's CPU for that work, and the child's unmapping of the runner's address space at exec counted too. With a 340 MB runner in a Linux container a `/bin/true` that runs 0.2 ms read 5.2 ms wall and 2.4 ms CPU on the cgroup meter (4.3 ms and 2.2 ms on the rusage meter), and the rusage meter reported 339 MiB of peak RSS for it (the runner's own peak, which exec carries over into `ru_maxrss`). A cgroup migration also waited for an RCU grace period now and then (a write to `cgroup.procs` took 11 ms against 0.02 ms usually), which made the wall time of short commands bimodal. The harness now starts through a gate (`arena/runner/launch.py`): a small Python shim blocks while the runner joins the cgroup, pins the process, opens the counters (`perf_event_open` on the pid, `enable_on_exec`) and reads its baselines, then it execs the harness. The clock starts when the shim's close-on-exec pipe closes, which is the exec; CPU is `usage_usec` less its reading before the join (a systemd scope's holder process is in it), or `wait4` rusage less the shim's CPU at the gate. The same process now reads 0.17 ms wall and 0.6 ms CPU (cgroup) and 0.23 ms and 0.55 ms (rusage), against 0.2 ms and 0.15 ms for a bare vfork and `wait4`; the 0.4 ms difference is the shim's wake-up and exec. The rusage meter on Linux no longer reports a peak RSS at or below the runner's own peak (it uses the sampled value, or none). A PTY run still forks (the controlling tty is set in the child) and keeps its clock at the exec. `docs/METHODOLOGY.md` section 4 says where a sample starts. `tests/test_spawn_clock.py` runs `true` through every meter this host has and compares it with a direct start.

- Launch pins: `pi-node` and `pi-bun` move from Pi 1.1.0 to Pi 1.3.0 (install pair and release binaries of the v1.3.0 release); `pibolt` moves from Pi-Bolt 0.7.4 to 0.9.3 (Pi 1.3.0, linux-x64 and darwin-arm64, SHA256SUMS signature checked with Pi-Bolt's Ed25519 release key). `opencode-v2` (2.0.29) and `claude-code` (2.1.296) are unchanged.
- Ticket-1 pins: `pig-tip` is rebuilt from PiG integrate-042 at 56503881e17f (tree 388853cdd6eb) with the release build's flags (`-trimpath`, `-s -w -X ...cli.Build=<commit>`, CGO off); a new arm `pi-bolt-0.8.5` pins Pi-Bolt 0.8.5 (release 2026-10-12, stock AOT linux-x64 and darwin-arm64 archives, checksums verified against the release's SHA256SUMS). Both pass `arena arm verify` (version, print, rpc and pty on every wire API). arms.lock regenerated. `campaigns/ticket1.toml` is the ticket-1 plan for those four arms (overhead, ext10, streaming, longsession).
- The quiet gate ignores kernel threads (a thread with `PF_KTHREAD`, pid 2 or a child of pid 2): they cannot be moved off the bench CPUs and made the gate wait 93% of a sample's time on a host running a per-CPU tracing agent. Only user-space runnable threads count against `--quiet-max-runnable`; every sample records `cpuset_kthreads` (how many were ignored) and, when any, `ignored_kthreads` (their names).
- Faithfulness is graded (probe set v0.2): identical 1.0, equivalent-presentation 0.9, equivalent-semantics 0.6, behaviour-differs 0.0, decided by a deterministic comparator per probe family (`arena/faithfulness/grading.py`). F4 session format weighs 15 and F1 CLI surface 5 (machine-facing dimensions outweigh human-facing). `faithfulness.json` scores carry per-class counts, `credit` and `correctness_failures`; the grade zeroes core, ext10 and long-session for an entry with a correctness failure and never gates on presentation.

### Fixed

- The container relay no longer adds `ARENA_RELAY_ADDR` to an arm's environment (an uncontained arm does not see it); `-export-addr` turns it on for a caller that binds port 0.
- `arena index --immutable-against REF` and the results workflow measure a change from its merge base with HEAD: a base branch that moved after the fork no longer makes a submission look as if it edited the files that landed there.

### Changed

- Container samples carry cgroup telemetry: `ContainerMeter.close` notifies the close listeners and the collector records the relay's final reading of the container's cgroup as `cgroup.mode = "container"` (arm CPU, throttling, memory and pid peaks). A throttled container is RED; a container sample is not judged against the session's own CPU quota.
- macOS with `--isolation container`: the site's `cpus` are the container VM's CPU ids and go to `--cpuset-cpus` (the local backend accepts `cpus` and `pinning = "required"` for that run, `Plan.vm_cpus`); the run is labelled PROVISIONAL with its reason. `Backend.check` takes the run's `isolation`. New `sites/example-macos-container.toml`. Without container isolation `cpus` is still refused where the platform cannot pin. Tested with a fake runtime (argv and lint), not against a real Docker VM.
- macOS portability: no call needs `os.sched_getaffinity` or `/proc` any more. A platform without CPU affinity runs unpinned and says so in the run's PROVISIONAL reasons (`pinning = \"required\"` is refused there); `sites/example-macos.toml` is the profile (`pinning = \"none\"`, no `cpus`). The egress audit lists the tree's sockets with `lsof` where there is no `/proc` (`egress.source = \"lsof\"`), and `arena verify` refuses a run whose platform had neither. The `rusage` meter, the process census, the quiet gate's load reading and the host-lock inheritance check have `ps`, `getloadavg` and `fcntl F_GETPATH` fallbacks. CI runs the suite on Linux and macOS, one way only: `python3 -m unittest discover -s tests -t .`.
- A run on several Kubernetes nodes seals each node's run directory with the cluster's files. Before this, `arena verify` rejected every node directory of a multi-node run (calibration and campaign families) on its seal.
- `cluster-facts.json` no longer states `qos: Guaranteed` without checking; the API server's QoS class is in node.json.
- A session that runs from a bundle records the bundle's commit and tree as the runner's (it has no `.git`), checks its files against `ARTIFACTS.sha256`, and records `runner.bundle_sha256`. Before this, every bundle run had no runner commit, and `arena verify` rejected it.
- `bundle.json` records whether the arena checkout was dirty (`dirty`, `diff_sha256`). A session that runs from a bundle built with `--allow-dirty` from a dirty checkout, or from a bundle whose `bundle.json` does not say it was clean, is dirty, so `arena verify` does not accept its runner commit for code that is not that commit.
- A resumed campaign is refused when its bundle differs from the one its finished steps ran from.
- The quiet gate no longer blocks on iowait (R9 section 8, row 12: the kernel documents it as unreliable). `pinned_iowait` is still recorded in every sample; `--quiet-max-iowait` and the site key `quiet_max_iowait` are removed.
