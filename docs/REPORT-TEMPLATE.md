# The report template

A report is generated by `buffon report` from the raw samples of a run, and from nothing else. This page shows the layout of a report. It is a template and not a result, so every value is a placeholder in angle brackets, and no number on this page is a measurement. `buffon verify` regenerates a report and rejects one with an edited number ([RUNNING.md](RUNNING.md)).

The memory section is the part this page spells out, because "memory" names four different readings and a reading depends on when it is taken. [LIMITATIONS.md](LIMITATIONS.md#4-memory-means-different-things) says why.

## Sections of a report

In the order `report.md` prints them. A section marked *when* appears only when the run has the data for it.

1. **Run notes**: every run-health check with its value, usual range and meaning, the notes first ([HEALTH.md](HEALTH.md)).
2. **Buffon leaderboard: Pi Harness Score** (*when* the run has cells to grade; it is graded with what there is, and lists what is missing and the run's trust badge): the leaderboard tables, the entries below the reference, the losses first, and why a cell is not a score ([GRADE.md](GRADE.md)).
3. **Summary by axis**: one row per arm and axis, with the ratio to the reference.
4. **Races** (*when* the run has samples on a ladder of growing load: extensions, session size): one race per ladder, the finish line and limits once, then one lane per harness with its outcome (Finished with the time, or Stopped with the rung, the time and the cause), speed, memory, reliability and resources ([TRACKS.md](TRACKS.md)).
5. **`<arm>` against `<reference>`**: one table per arm, with one row per workload, API and metric (below).
6. **`<arm>` against its previous arm** (*when* a manifest declares the arm it replaces): the change between the two.
7. **A/A noise floor**: the reference against a copy of itself, per metric.
8. **Cell ids and rerun commands**: the id of every cell, for `buffon rerun`.
9. **Noise report**: how noisy the run was, from its samples and the telemetry around each: A/A gaps, spread, outliers, drift, throttling and flagged samples ([TELEMETRY.md](TELEMETRY.md)).
10. **Soak** (*when* the run has it): resource series over minutes, and whether each is flat.
11. **Reliability** (*when* the run has it): the fault scenarios each arm passed.
12. **Failures, cannot-run and egress**: every failed sample, every arm that cannot run a workload and why, and the egress audit.
13. **Not measured**: families and metrics a run did not cover, and why.
14. **Provenance**: the pins of every arm, as the run recorded them.
15. **Arms and environment**: versions, executables, install footprint, and the host.
16. **Piglet arms** (*when* the run has them).
17. **External results** and **External suites** (*when* the report includes them): other projects' results, kept out of every aggregate ([EXTERNAL.md](EXTERNAL.md)).

## The HTML report

`report.html` has the same content as `report.md` in a designed page, in this order:

1. A header with the brand mark, the headline, and badges for PROVISIONAL (or quiet dedicated hardware), the number of run notes, the reference and the grade method.
2. **The grade and faithfulness**: one card per entry with its score, the table it is ranked in, its coverage, and its faithfulness score on a bar with the floor marked.
3. **Families**: one card per grade family, and one for the cells the grade does not score. A row gives the workload and metric, the kind and unit, a memory metric's kind (peak RSS, RSS, PSS and so on), the two medians, the ratio with its interval, the spread (IQR and CV) and the A/A floor, an arrow and words that say where the arm's median sits against the reference's, and the command that reruns the cell. The arrows never say whether a position is good.
4. **Full report**: every section of `report.md`, and the drift plots.
5. **Limitations**: [LIMITATIONS.md](LIMITATIONS.md), embedded.

The file is static. It carries its CSS, uses the system's serif, sans and monospace fonts, draws the brand mark as an inline SVG, and fetches nothing when it is viewed. The numbers are the strings `report.md` prints: the page and the Markdown are built from the same helpers.

## A row of a table

```
| workload | api | metric | kind | unit | n | reference median | arm median | ratio [95% CI] | A/A floor | MDE | CV ref / arm | IQR ref / arm | outliers ref / arm | p (Holm) | equivalent (TOST) | note | cell |
| <workload> | <api> | <metric> | <wall, CPU, memory, size or wire> | <unit> | <n> | <median> | <median> | <ratio> [<low>, <high>] | <floor> | <mde> | <cv> / <cv> | <iqr> / <iqr> | <count> / <count> | <p> | <yes or no, and the margin> | <note> | <cell id> |
```

A row is one kind. Wall time, CPU work, memory, size and wire are separate rows, and a row never mixes them.

## Memory

### Four kinds

Each kind is its own column in the memory table, and the report names it. Footprint can sit far below RSS, because RSS counts shared libraries and pages that other processes also map.

| kind | the question it answers | read from | state |
|---|---|---|---|
| own footprint | how much memory does this process hold that no one else shares? | macOS `ri_phys_footprint`; Linux `smaps_rollup` `Private_Dirty` | planned |
| RSS | how many pages of this process are in RAM now, shared pages included? | process tree, sampled | produced as `rss_mib` (soak) and `ready_rss_mib` (long-session resume) |
| peak RSS | what is the most RSS the process reached? | `getrusage` `maxrss`; for a cgroup, `memory.peak` | produced as `peak_rss_mib` and `peak_mem_mib` |
| heap in use | how much does the runtime itself say it uses? | the runtime's own report, where the arm exposes one | planned |

One further reading is produced today and is not one of the four: `pss_mib` and `ready_pss_mib`, the proportional set size (each shared page divided among the processes that map it), on Linux.

### Sample times

A memory reading right after an answer differs from the reading at rest, so each sampled kind is read at fixed times after the last answer and each time is its own column.

| column | time after the last answer | state |
|---|---|---|
| +30 ms | 30 milliseconds | planned |
| +2 s | 2 seconds | planned |
| +10 s | 10 seconds | planned |
| whole-run peak | the whole run; peak RSS only, which has no sample time | produced |

Today a run reads memory at the point a workload defines (for example when the process is ready, or at each soak interval) and not at these three times.

The **headline time** is declared per workload in its definition, before a run, and is the same for every arm. The row prints which time it is. The report never picks the most favourable time after seeing the results.

### The memory table

```
| workload | arm | kind | unit | headline time | +30 ms | +2 s | +10 s | whole-run peak | n | note |
| <workload> | <arm> | own footprint | MiB | <+30 ms, +2 s or +10 s> | <median> (IQR <iqr>) | <median> (IQR <iqr>) | <median> (IQR <iqr>) | — | <n> | <note> |
| <workload> | <arm> | RSS | MiB | <headline time> | <median> (IQR <iqr>) | <median> (IQR <iqr>) | <median> (IQR <iqr>) | — | <n> | <note> |
| <workload> | <arm> | heap in use | MiB | <headline time> | <median> (IQR <iqr>) | <median> (IQR <iqr>) | <median> (IQR <iqr>) | — | <n> | <note> |
| <workload> | <arm> | peak RSS | MiB | whole run | — | — | — | <median> (IQR <iqr>) | <n> | <note> |
```

Three kinds of empty cell mean three different things, and a report never uses one for another.

- **`—`**: not defined for this kind. Peak RSS has no sample time, and the sampled kinds have no whole-run peak.
- **`n/a: <reason>`**: the arm cannot give it. A runtime that does not report its heap has `n/a: heap not exposed`.
- **`not run`**: Buffon does not produce this column yet. A reader sees that the column exists and has no data.

A reading that is not available is null and is never written as 0.

### What a note should say

The note says what a reader needs to interpret the row. The notes below are the layout's intent; the generated report does not write them yet.

- **Idle behaviour of the runtime.** A runtime that returns memory slowly after work, such as one with a lazy garbage collector, shows a higher value at +30 ms than at +10 s. The note names it. Buffon does not hide it by choosing a later time, and it does not force a collection.
- **The platform.** A Linux row comes from a cgroup and a macOS row from rusage and `ps`. The two are not compared with each other. On macOS the footprint also depends on the runtime's allocator ([LIMITATIONS.md](LIMITATIONS.md#why-a-macos-footprint-depends-on-the-allocator)), and Linux `Private_Dirty` is the like-for-like figure.
- **The design a row favours.** A workload that repeats content favours a harness that deduplicates it, and the note says so next to the numbers ([LIMITATIONS.md](LIMITATIONS.md#5-some-metrics-favour-a-design)).

## Checks on this page

`tests/test_docs.py` checks that the sections named here are the ones `render.py` prints, that the four kinds and three times here are the ones in METHODOLOGY, that the metric names this page says are produced exist in the code, that the template holds no number, and that its "planned" state is true while the code does not read a footprint or a sample time after an answer. When that changes, the check fails and this page must change with it.
