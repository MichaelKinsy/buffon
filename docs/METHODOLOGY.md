# Methodology

How every Buffon number is produced. A report that departs from any rule here says so at the top, with the reason. What each family measures is in [WHAT-WE-MEASURE.md](WHAT-WE-MEASURE.md). What a number cannot tell you is in [LIMITATIONS.md](LIMITATIONS.md).

## 1. Pinned versions

- Every arm is installed from one exact artifact: a release archive, a single binary, or a package installed from a committed lockfile (`npm ci --ignore-scripts` from the release's own install lock where one exists). Floating installs (`npm i -g pkg@latest`, `curl | sh` without a version, `go install …@latest`) are never used.
- Every artifact is checked against a sha256 in `arms.lock`. Where the project publishes `SHA256SUMS` or a signature, the lock records it and the installer checks both. Where a project publishes no checksum, the lock records the hash of the first download, marks it `trust: first-use`, and the report says so.
- Source-only arms are built from a commit hash, with the toolchain pinned by version and checksum, and the build flags recorded.
- The runtimes the arms need (Node, Bun, Python) are pinned the same way. Buffon never uses whatever runtime the host happens to have.
- `arms.lock` is generated from the arm manifests by one command. Its sha256 is printed in every report. After a run, the runner checks that every executable is unchanged.
- Self-update is disabled for every arm (its environment variable or config key is in the manifest). A run fails if an arm's version string changes during the run.

A manifest may declare `previous = "<arm id>"`: the earlier arm it replaces (a release, an older build). The report then shows, for that arm only, the change between the two on every row and in its own section, with the same A/A floor rules and losses first. Any arm may declare it; Buffon has no built-in pair.

Container isolation (`--isolation container`, docs/ENVELOPE.md) differs from `none` in these ways, each stated in the run's record: the arm runs as the invoking user's uid:gid inside a read-only root with a tmpfs HOME; every measured interval runs from the instant the relay starts the arm to the instant it exits, both read from the host's monotonic clock (a container has no time namespace), so the container's creation, which varies per sample by more than the arm's own time, is not in it; the envelope's own cost (`null_run_ms`, the median of `/bin/true` started the same way) is reported and never subtracted; and HOME is a fresh tmpfs seeded from the harness's HOME for each container, that is for each process, so in a sample with several processes (longsession grow then resume) the second process starts from the seed again, where an uncontained one sees what the first wrote (caches, settings). A result's isolation stamp says which applied.

## 2. Isolated HOME

- Each process gets a fresh, empty HOME and a fresh temporary directory, created for that repetition and deleted after it. The arm's own state directories (`~/.pi/agent`, `~/.omp`, `CODEX_HOME`, `COPILOT_HOME`, `XDG_*`) point inside it.
- The only files placed in it are the ones the arm's config writer produces: the mock endpoint, a dummy API key, the workload's settings. No real credential is ever present on a benchmark host.
- **Proven, not claimed.** Every sample records `home` in raw.json (docs/RAW-FORMAT.md): that its directory was created new (`fresh`; a leftover of an earlier sample is removed and the sample says it was not fresh), what the home held before the process (file count and a sha256 over every file's path, size and, up to 256 KiB, content) and what it held after (the same, plus the files the process wrote). `buffon verify` rejects a run where a sample has no proof, was not fresh, or started from another state than the arm's other rounds of the same workload and API. Warm rows start from the arm's seeded first-start state (what a user pays once); the cold-home cost is its own row (`devloop/first-run`, section 12) and is never mixed into a warm row.
- The runner strips every inherited variable that an arm reads (`PI_*`, `PIG_*`, `NODE_*`, `BUN_*`, `CLAUDE_*`, `CODEX_*`, `COPILOT_*`, `OPENAI_*`, `ANTHROPIC_*`, `GO*`), then sets the arm's offline and telemetry-off variables from its manifest.
- A run fails if machine-level configuration for any arm exists (for example `/etc/claude-code`, `/etc/codex`), because no flag overrides it.
- **Egress.** Each arm runs in a network namespace whose only route is the loopback mock, or, where namespaces are unavailable, its sockets are sampled every 25 ms and any connection to a non-loopback address fails the run and the report. The report says which method was used.

## 3. Mock model

- One scripted mock serves OpenAI Chat Completions, OpenAI Responses and Anthropic Messages (with `count_tokens`), streamed as SSE, with `TCP_NODELAY` set on every socket (Nagle's algorithm with delayed acknowledgement once added about 40 ms per turn to harnesses that reuse connections).
- Each workload names a policy: for example "call `read` on the named file, then answer", "stream N characters at R tokens per second", "answer the compaction request", "send only keepalives". The same policy, seed and fixtures go to every arm.
- The mock reports deterministic usage so harnesses that compact on usage behave the same way every run: prompt tokens are the request's wire bytes divided by 4 and completion tokens are one per streamed part plus 12 per tool call. No tokenizer is pinned yet, so these are an estimate that is identical for arms sending the same request, not a provider's count; a harness whose request is larger sees a larger prompt and compacts earlier, which is part of what is measured. When a tokenizer is pinned this section and RAW-FORMAT.md change together.
- The mock logs every request: arrival time, reply start and end, wire bytes, and the full body. Harness time per turn is wall time minus mock time, measured at the mock.
- Faults (HTTP 429/500, a stream dropped before or after the first byte, keepalive-only streams) are injected by the mock, at a scripted point, identically for every arm.
- An arm whose wire API the mock cannot serve (for example a harness that only speaks Gemini's API) gets "cannot run" for every workload until the mock supports it.

## 4. Measurement

- **Every arm runs from disk.** An arm's binaries, runtime images and caches are never on tmpfs or in shared memory, because the footprint (Private_Dirty) counts code mapped from them as the process's own memory (about 40 MB for a runtime image). A harness's HOME holds config and state (it is a tmpfs in a container); its runtime code and caches (`PIG_HOME`, `TMPDIR`, `XDG_CACHE_HOME`, a seed's unpacked natives) are on `disk/` beside it under the run's work directory, in a container too (a manifest names such a variable with `{disk}`; a test rejects one that puts a cache or runtime directory in `{home}`). The runner refuses a work directory that is on tmpfs or ramfs and records its file system (`run.work_fs`), and refuses an installed arm whose executable (its real path, which for a source-built arm is in the cache directory) or a runtime directory on its PATH is on tmpfs or ramfs. While a sample runs, the runner reads the executable mappings (`/proc/<pid>/maps`) of every process of the tree against the process's own mount table and records the file systems in the sample (`text_fs`: files per file system type, and `bad`); a mapping from tmpfs, ramfs, `/dev/shm`, `memfd:` or SysV shared memory **fails the sample**, naming the file. The reading is taken at most every 0.2 s while the tree runs, so a sample that ends before the first one (a `--version` of a few tens of ms) has no `text_fs`, and a short-lived child between two readings is not seen; the install-time check covers the arm's own executable and runtimes. Anonymous executable memory (a JIT's code) is not a file and is never flagged.
- **Instructions are the headline CPU metric.** Where the host allows it, every sample records `instructions` and `cycles` of the whole process tree: Linux `perf_event_open` counters opened on the process while it waits at the launch gate, before its exec (`inherit`, `enable_on_exec`), so Buffon's own start-up work is not counted and every thread and process the harness creates is; user and kernel instructions when `perf_event_paranoid` <= 1 or the process has CAP_PERFMON, user-space only at paranoid 2 (`perf_scope` says which, per sample). macOS reads `ri_instructions` and `ri_cycles` from `proc_pid_rusage` for every process of the tree, sampled with the tree sampler (`perf_scope` is `sampled`: a process that exits between two samples loses its last interval; verify an instruction number on macOS against a Linux host before relying on it). A host that allows neither, and the container envelope, have no instruction cells and `run.perf` says why; the report's header then names CPU time the headline for that run. Instruction counts do not depend on the clock speed and are far less noisy than time, but they are not energy and not wall time: a harness that waits costs few instructions and much time. **CPU time** (user + system, wait4 or the cgroup) and **wall time** (elapsed) sit beside them as their own cells. Every cell names its kind (wall, CPU, memory, size) and its unit; a row never mixes kinds. In the grade, instructions supersede CPU time as a workload's CPU cost (CPU time stays in the report), so one CPU cost is never counted twice.

- **CPU and memory**: each arm's process tree runs in its own cgroup v2. CPU comes from `cpu.stat`, peak memory from `memory.peak`, and peak RSS is the maximum over 25 ms polls of the summed `VmHWM` of the live processes (`buffon/runner/cgroup.py`, `_sample_rss`). PSS is read once, at the ready moment (`current_pss_mib`), not sampled. Where cgroups are unavailable (macOS), the runner uses `wait4` rusage and `ps` samples, and the report labels the arm's numbers as rusage.
- **A sample starts at the harness's exec.** Where the host allows it (Linux and macOS, always except a PTY run), the runner starts the harness through a small gate (`buffon/runner/launch.py`): a Python shim that waits while the runner joins the cgroup, pins the process, opens the counters and reads its baselines, and then execs the harness. The runner's own fork, the cgroup migration (which can wait for an RCU grace period) and the counter set-up all happen before the gate opens. The clock (`t_spawn`, every `*_ms` interval and `wall_ms`) starts when the shim's close-on-exec pipe closes, which is the exec. CPU is the cgroup's `usage_usec` less its reading before the join (`cpu.stat` of a systemd scope includes its holder process), or on the rusage meter `wait4`'s rusage less the shim's CPU at the gate (read from `/proc` on Linux, `proc_pid_rusage` on macOS). `memory.peak` starts empty of the runner's pages for the same reason. What stays in the numbers is the wake-up of the shim and its exec, about 0.3 ms of CPU and under 0.1 ms of wall, which a direct start of the same process pays too. A direct measurement of `/bin/true` (vfork, `wait4`) agrees with the meter within 1 ms. A PTY run (the terminal's controlling tty is set in the child) forks the runner instead: its clock still starts when Popen returns, after the exec, and the pre-exec CPU of the child is subtracted on the rusage meter, but the cgroup meter counts the child's unmapping of the runner's address space at exec (about 1 ms per 100 MB of runner) as CPU of the harness. On the rusage meter on Linux `ru_maxrss` of any child of the runner is at least the runner's own peak (exec carries the old address space's peak over), so a value at or below the runner's peak is dropped and the sampled `VmHWM` is used, or no value when no sample was taken.
- **Per-turn CPU** is the difference of two `meter.cpu_ms()` readings (the cgroup's `usage_usec`, or on the rusage meter the process CPU clocks or `ps`), taken at the end of the previous turn and at the end of this one (`buffon/workloads/overhead.py`, `drive_turns`). It is not made from schedstat.
- **Run-queue wait.** Every sample also records the schedstat totals of its process tree (`sched` in RAW-FORMAT.md): CPU time, the time its threads were runnable but waiting for a CPU, and the number of timeslices. Wait time is a direct per-sample reading of CPU contention. It is recorded beside the metrics and never gated or compared; no report or grade code reads it as a metric.
- **Wall time** comes from a monotonic clock in the runner, and from the mock's timestamps for anything between a request and its reply.
- **Interactive runs** use a real PTY of a fixed size, driven by a scripted terminal that answers terminal queries the same way for every arm. Terminal answers change code paths (DA1, the kitty keyboard protocol, OSC colour and size queries), so Buffon publishes the exact terminfo entry and every query reply, and runs two terminal profiles: `xterm-256color` with no extended protocols, and a kitty-like profile with the keyboard protocol, synchronized output and OSC replies. Each profile is reported separately.
- **Cold and warm starts.** A warm start follows a start of the same arm in the same round. A cold start uses one of two methods, named in the report for every cold number: `drop_caches` (the host's page cache is dropped before the start, which needs root on a dedicated host), or a fresh container whose image layers are not in the page cache. Numbers from the two methods are never compared with each other.

### Measurement caveats by platform

An accuracy audit of the code found four places where the macOS and rusage meters measure less than the cgroup meter. They are in the code today. The statistics downstream are not affected; the inputs are. Meter names are those recorded in each sample's `meter` field.

- **Instructions on macOS are sampled and undercount.** The `rusage` meter reads `proc_pid_rusage` (`ri_instructions`, `ri_cycles`) of each tree member from its own sampling loop, about every 165 ms (on the machine audited) (a 0.1 s sleep plus the cost of `ps -A` and `lsof`), and a process that exits between two reads loses its last interval (`buffon/runner/perfcount.py`, `MacTree`; `perf_scope = "sampled"`). On one Mac, the same 300 ms loop counted 4.5e9 instructions with the default `lsof` interval and 6.5e9 with a 10 ms one (+44%). The undercount depends on how long a process lives. Where an instruction cell exists the grade leaves the CPU-time cell out, so on macOS the grade's CPU cost is this sampled count. Linux `perf_event_open` counts from exec to exit and does not have this problem. Treat macOS instruction counts as indicative, and compare them only between arms measured by the same loop.
- **A live CPU reading on the `rusage` meter forgets processes that already exited.** `RusageMeter.cpu_ms()` before `wait4` sums the processes alive at that moment; the value after `wait4` includes reaped children. `ready_cpu_ms`, `turn_cpu_ms`, `first_request_cpu_ms`, `extensions_ready_cpu_ms` and the start side of the `*_cpu_ms_per_1k_tokens` metrics are differences of live readings, so a helper that exits during the window is missed, and a per-turn difference can be negative. The cgroup meters (`cgroup-direct`, `cgroup-systemd`) read `usage_usec`, which keeps exited tasks, and are not affected. A Kubernetes pod uses the `rusage` meter when its cgroup is read-only (`buffon/runner/cgroup.py` docstring) [INFERENCE: not run in a pod].
- **On macOS the RPC, resume and long-session memory cells are missing.** `RusageMeter.max_proc_rss_mib()` returns `None` while the process runs on a host with no `/proc`, and the RPC and long-session workloads call it before the process exits. `peak_rss_mib`, `ready_rss_mib` and `extensions_ready_rss_mib` are then null in `raw.json` and no cell exists. Print and PTY peak RSS are read after exit and work (`ru_maxrss`, the largest single process, not a sum). PSS is not available on macOS. The macOS grade therefore scores the `core`, `ext10` and `long-session` families from fewer cells than a Linux run does.

- **All-processes peak memory on macOS was sampled too late for a short command.** `RusageMeter` reads the tree with `ps -A` (and `lsof` for the egress audit) from a sampler thread, and one pass takes tens to hundreds of milliseconds on a busy host. A command shorter than that exits before the first sample lands, or after a first sample that caught it just after its exec, before it had touched its pages. `peak_mem_mib` then read a few tens of KiB for a process whose `ru_maxrss` was 15 MiB, and an OpenCode start-up memory cell came out 2121 times the reference. Now a sample counts only when it saw the tree with a resident set; with none, `peak_mem_mib` is missing (no cell), never zero. With one, on macOS the value is never below the largest single process's `ru_maxrss` from `wait4`, since the sum over all processes cannot be smaller than its largest member. `peak_rss_mib` (the largest single process) always came from `ru_maxrss` after exit. A short command on macOS can therefore have a `peak_rss_mib` cell and no `peak_mem_mib` cell.

A macOS run is PROVISIONAL for these reasons as well as for pinning. Do not compare a macOS number with a Linux number ([LIMITATIONS.md](LIMITATIONS.md) sections 10 and 11).

## 5. Host and noise

- A headline in the results index needs a machine that runs nothing else: dedicated bare metal, or a Kubernetes pod with Guaranteed QoS on a node pool reserved for the run, with CPUs pinned (exclusive cores). Any other host still measures. The run is recorded in full and labelled (PROVISIONAL, and a reason on the trust badge, section 18); it is never refused unless `--require-class A` is set.
- The CPU frequency governor should be `performance` or the clock fixed. A dynamic governor is a note on the run and the run is labelled Shared; only `--require-class A` refuses it. Turbo and SMT state are recorded.
- The report records the host: CPU model and features, core count, memory, kernel, governor and clock, cgroup limits, and, for every sample, what the machine, the pinned CPUs and the sample's cgroup were doing before, during and after it (section 13).
- **Interleaving.** Arms run in interleaved rounds: every round runs every arm once per workload, in an order rotated each round, so drift on the host lands on every arm equally. The order is a deterministic rotation (`rotate` in `buffon/runner/engine.py`: variants rotate by the round number, arms by the round number plus the variant's index), not a shuffle. The warm-up is the first `--warmup` round or rounds (default 1): every arm in every variant, flagged `warmup: true`, dropped from the statistics and kept in the raw data.
- **Repetitions.** At least 12 measured repetitions per arm and cell; more where the A/A floor says the cell is noisy.

### Serial execution on the host

Measurement is strictly serial. These rules are enforced by the runner, not left to the operator:

- **One harness process at a time.** Samples run one after another in interleaved round-robin order, rotated each round; nothing measured overlaps with anything else of ours. The soak runs its arms one after another, each for the whole soak.
- **One measurement per host (slots excepted).** The one exception is the opt-in slot mode below, where several sessions run at once on disjoint cores under conditions the runner checks. Otherwise the runner takes an exclusive lock (`--lock-file`, by default in the temporary directory) for the whole run and refuses to start while another Buffon run holds it. A site may also name lock files that other benchmark tools on the host hold (`[local] lock_files`, `--foreign-lock`, for example a host-wide bench slot); the run then refuses to start while someone else holds one, and a run started inside the holder's wrapper (which owns the lock through an inherited descriptor) is let through. Run measured commands inside your host's bench-slot tool when it has one; builds and downloads stay outside it.
- **A quiet check before every sample, on the benchmark's own CPUs.** The check looks at the pinned CPUs (the benchmark's CPU set), not at the whole host: another workload elsewhere does not matter, a task on these CPUs does. Over a 0.25 s window the largest per-CPU busy share must be at most `quiet_max_busy` (default 10%), steal at most `quiet_max_steal` (2%); at most `quiet_max_runnable` (default 0) other **user-space** threads may be runnable with their last CPU in the set (kernel threads are ignored: they cannot be moved off the bench CPUs, and a host security or tracing agent runs per-CPU workers such as `bpfrb/N` and `evdefer/N` on them; a kernel thread is one with `PF_KTHREAD` set, pid 2, or a child of pid 2; the count is recorded per sample as `cpuset_kthreads` and the names as `ignored_kthreads`, so a reviewer sees what was ignored; the run-queue wait of the sample's own tree and the A/A floor still show any effect they have); the runner's cgroup must not have been CPU-throttled during the window; and CPU pressure (PSI `some avg10` of the runner's cgroup, the system's when the cgroup has none) must be at most `quiet_max_psi` (10%). A reading the machine cannot provide (no cgroup, no PSI) is recorded as null and never blocks. Otherwise the runner waits, up to `quiet_timeout_s` (default 300 s). A sample for which the CPUs never quieted down fails with the reasons recorded and starts no process.
- **The host is recorded per sample.** Every sample in `raw.json` carries the gate's readings (`pinned_busy`, `pinned_iowait` (recorded, never gated), `pinned_steal`, `cpuset_runnable` (user threads), `cpuset_kthreads` (kernel threads ignored), `ignored_kthreads` (their names, when any), `throttled`, `psi_cpu_some_avg10`), the whole host's `host_load1` and `host_runnable` (recorded for the record, never gated on) and `quiet_wait_ms` (time spent waiting); `run.quiet_gate` records the settings, how many samples waited and how many gave up. A run in which any sample waited more than a second or gave up is PROVISIONAL, with that stated.
- **Kubernetes.** A pod is one whole session (every arm and A/A copy, interleaved and sequential inside the pod) with Guaranteed QoS and exclusive pinned cores, so inside a pod the rules above apply unchanged. Pods run in parallel only on separate nodes (`buffon-cluster run -spread N` takes N distinct nodes, one session each); two sessions on one node at a time are the operator's error, and a node pool that is not reserved for the run makes the result PROVISIONAL.
- Results taken before these rules existed, on shared hosts, with concurrent sessions, stay PROVISIONAL and are never published.

### Slots on one big host

Serial measurement uses about 8 cores of a 48 or 128 core host. `[local] slots = N` (default 1: today's behaviour) lets `buffon campaign` run N sessions at once on one host without weakening the method. It applies only when all of these hold; the runner enforces them:

- **Disjoint whole cores.** The CPUs the runner may use are split into N slots of whole physical cores (SMT siblings are always in the same slot). One core is left to the host. Each slot has its own harness CPUs and its own mock CPUs, sized like the site's single session (`cpus` and `mock_cpus` give the counts; the mock gets whole cores). Slots are placed one NUMA node at a time, so a slot is on one node while any node has room for it; a slot spans nodes only when none does, and the dry run says so. A split that would share a core, name a CPU the runner may not use, leave a slot with fewer harness CPUs than the site's session, or that the host cannot hold is refused, before anything runs. A session whose CPU count does not fill whole cores is refused too.
- **A slot calibration, before any family.** The reference arm against its A/A copy (the plan's `[calibrate]` workloads and rounds, without the session's own gate) runs once alone in the first slot, and then in every slot at the same time. A slot passes when its CV of `cpu_ms` is at most 5% (`CV_GATE`) and, for each cell, the median of `cpu_ms` and of `wall_ms` (both copies together) is within the solo run's A/A floor of the solo median, in either direction. Concurrency must not move the numbers. The solo run must itself be within the CV gate and have a floor, and the concurrent sessions must have overlapped for at least half of the shortest one; otherwise no slot passes. The verdict, with every slot's reasons and numbers, is `slots-calibration.json`.
- **A failed slot is not used.** If no slot passes, the campaign runs serially on the site's own CPUs, as with `slots = 1`, and says so.
- **One session per slot, pinned to it.** Each family is one `buffon run --slot N` session in its own process with its own lock file (`<host lock>.slotN`). A slot's session holds the host-wide lock shared, so any number of slots run together and a serial run (which holds it exclusively) neither starts beside them nor lets them start. The quiet check looks at the slot's own harness CPUs; the CPUs of the other slots are not housekeeping CPUs for the host-class check.
- **A ratio never crosses slots.** A ratio is between arms of the same session, so of the same slot (section 7). Two families run in two slots are never compared with each other.
- **The trust badge.** A session in a slot whose calibration did not pass (or was not given, as in `buffon run --slot N` by hand) carries the reason `slotted` and is not Verified. A passed slot calibration adds nothing. `raw.json` records `run.slot` (`id`, `of`, `cpus`, `calibration`).

What slots do not do: they do not make the sessions independent of shared hardware that the calibration did not stress (the last-level cache, memory bandwidth and the disk of a family heavier than the calibration workload). Each session still has its own A/A copies and its own quiet check, which is where that shows; read the slotted run's A/A floor as for any run.

### On a cluster

A ratio is valid only between arms measured in the same rounds on the same node. A cluster run follows these rules (`buffon campaign`, docs/RUNNING.md, "Campaigns"):

- **One session is one family on one node.** Every arm of the family and every A/A copy runs interleaved inside one pod on one calibrated node. Arms are never spread over nodes: a ratio between two nodes compares the nodes, not the harnesses.
- **Calibrated nodes only.** `buffon calibrate` measures the reference against its own copy on each node first. A family runs only on nodes whose calibration passed (`buffon run --calibration FILE --nodes a,b`).
- **Distinct nodes for parallel sessions.** Sessions run at the same time only on distinct nodes. No node runs two sessions at once (`buffon campaign --parallel`).
- **A reproduction pair.** Each family runs on two nodes: its node, and a second node as its reproduction. When a free calibrated node has another CPU model, the second node is that one. `buffon compare` checks the pair: a comparison reproduces when the two ratios agree within the larger A/A floor (or their intervals overlap) and the verdicts agree. A comparison is a headline only when it reproduces. With one calibrated node there is no reproduction, so no comparison from that run is a headline.
- **Node identity is recorded.** `campaign.json` records each session's node, CPU model, CPU set, QoS class, CPU manager policy and that node's own calibration noise. The report names each run's node and marks a report that pools several nodes; render one report per node.

## 6. A/A noise floor

- Every run includes an A/A comparison: the reference arm against a second, identical copy of itself (installed into its own root and run as a separate arm, interleaved like the others).
- For each metric, the A/A difference and its interval set the noise floor of that run on that host. A difference between two arms that falls inside the floor is reported as "no measurable difference".
- The calibration gate: before anything is measured the reference arm runs against its own copy for 12 rounds of `overhead/print`. A coefficient of variation of its `cpu_ms` above 5% (`CV_GATE` in `buffon/runner/engine.py`) labels the run Noisy and the run goes on; with `--require-class A` it refuses the run instead (`--allow-noisy` then continues). The run note `calibration_cv` uses a stricter usual range of 2% and is a note only ([HEALTH.md](HEALTH.md)). The A/A coefficient of variation of the measured rounds is also a note (`aa_cv_cpu`). No note rejects a run.

## 7. Statistics

- A cell shows the median of each arm's measured rounds. The per-arm medians have no interval of their own; the 95% percentile bootstrap interval (seeded; the seed is in the report) belongs to the ratio.
- Comparisons with the reference arm are paired by round: ratio of medians with a bootstrap interval, and a sign-flip test. Several arms are corrected with Holm's method.
- Parity and pass/fail metrics use exact McNemar where paired, and plain proportions with Wilson intervals otherwise.
- **Equivalence** ("same as the reference") is a test of its own, a two one-sided test (TOST) at alpha 0.05, with a margin declared before the run in `workloads/margins.toml` (`buffon/stats/margins.py`; the file is read from the checkout the report is built from). For each comparison whose metric has a margin, the report takes the paired ratio of medians (rounds paired, resampled by round, the same bootstrap draws as the ratio's interval) and its 90% percentile interval. The arm is **equivalent** when that interval lies inside 1/(1+margin) to 1+margin, which is the same as the 90% interval of the paired log ratio lying inside ±log(1+margin). `report.json` gives each comparison `equivalence`: `{"margin", "low", "high", "p", "equivalent"}`, where `margin` is a fraction (0.05 is ±5%), `low` and `high` are the 90% interval of the ratio, and `p` is the larger of the two one-sided bootstrap p-values; it is null where the file declares no margin. `report.md` has an `equivalent (TOST)` column (`yes ±5.0%`, `no ±5.0%`, or `n/a`). The margins:

  | metric | equivalence margin |
  |---|---|
  | CPU time, instructions, cycles, wall time | ±5% of the reference median |
  | peak and steady memory (`*_mib`) | ±5% or ±2 MiB, whichever is larger (the margin is the larger of 5% and 2 MiB over the reference median) |
  | bytes and tokens sent per turn (`*_bytes_per_turn`, `*_tokens_per_turn`) | exact: equivalent only when every paired round has the same value |
  | parity and pass/fail rates | ±0 cases (any difference is reported); the agent-bench lift compares them by exact McNemar, and no report cell carries these names today |

  A metric not listed (for example a total of bytes) has no margin and no equivalence claim.
- **"No measurable difference" and "equivalent" are different claims.** "No measurable difference" is the floor rule: the ratio sits inside the run's own A/A noise floor, so this run cannot tell the arms apart. It gets easier to reach as a run gets noisier. "Equivalent" says the data show the two arms within the declared margin: it needs a tight interval and gets harder as a run gets noisier. A noisy run can report a 20% gap as "no measurable difference" and still not be equivalent to within 5%. A quiet run can report a 2% gap as a loss (outside a floor of 1%) and still be equivalent to within 5%. Read the two columns together.
- Each cell also reports its **minimum detectable effect** at 80% power, computed from that run's A/A variance and repetition count, so "no measurable difference" can be read for what it is: a difference smaller than the stated size cannot be seen in this run.
- Resampling is by task or round, never by individual trial within a round.

## 8. Raw samples published

- Every published report ships with its run directory: every raw sample (one JSON line per measurement), the mock's request log including bodies, every harness's stdout and stderr, the PTY transcripts, host facts, the lockfile, the exact command lines, the seeds and the runner's own commit.
- Summary tables are generated from that directory by `report/`, and anyone can regenerate them from it.
- Nothing is published that the run directory cannot reproduce.

## 9. Losses reported

- Each arm's section lists every metric where it is measurably worse than the reference, as prominently as the metrics where it is better.
- An arm that crashes, hangs, times out or produces a wrong result in a workload is reported as such, with the log. A failed repetition is never dropped and retried silently: every attempt is in the raw data, and the report counts failures.
- An arm that cannot run a workload (no headless mode, an unsupported wire API, a missing feature) gets a "cannot run" row with the reason, checked against the arm rather than assumed.
- Figures use the same scale for every arm, start their axes at zero for amounts, and never omit an arm because its result is unflattering.

## 10. Changes to a published result

A methodology error found after publication is corrected in a new report that links the old one and states what changed. The old report stays available.


## 11. Run Rules v1

Adopted from the benchmarking review in the lead's handoff R9. `buffon verify` rejects a result that breaks an enforced integrity rule: the seal, `raw.json`, the isolation stamp, host disclosure, provenance and pins, the executables, and a run made without telemetry or without its A/A copies. Rules about how quiet or how dedicated the host was (noise, shared hardware, fewer than 12 rounds) are labels: `verify` lists them as notes, and they decide only whether a run is a headline (section 18). The runner and `buffon verify` enforce what the **Status** table says is enforced; a rule marked *planned* is a rule of the methodology that no program checks yet, and no result may claim it.

Host
1. MUST run on a declared host class: A = dedicated host or reserved node (exclusive CPUs); B = shared host, results PROVISIONAL. Site headlines: Class A, or Class B reproduced on Class A within the TOST margins.
2. MUST pass `buffon preflight` for its class: Class A needs bench CPUs exclusive (no foreign task may run on them), whole physical cores (SMT siblings reserved or offline), ≥1 housekeeping CPU, cpuset CPUs and mems on one NUMA node.
3. MUST use governor `performance`; Class A turbo off; Class B turbo state constant. MUST record effective GHz per sample.
4. MUST run with no CPU quota on the arm cgroup or any ancestor (`cpu.max` = max). k8s: Guaranteed QoS, integer CPUs, static CPU manager with full-pcpus-only, reserved-cpus set, single-numa-node.
5. MUST record `buffon sysinfo` (CPU, microcode, mitigations, nominal/max MHz, SMT, C-states, THP, ASLR, NUMA, IRQ steering, kernel, cgroup driver, container runtime/seccomp/storage, k8s and kubelet policies, image digests) in host.json.
6. MUST hold a host-global lock for the whole run, and only one measured process tree may run at a time.
Envelope
7. MUST pin every arm, runtime and image by sha256/digest. Self-update off. Egress only to the mock.
8. MUST use the same container envelope for every arm. MUST measure and report a null arm (container start + /bin/true) per round.
9. MUST pad the environment to a fixed byte count and use fixed-length HOME/TMP paths. HOME/TMP on tmpfs. Record the ASLR state.
10. MUST name the cold-start method per cold number. Class B MUST NOT publish cold numbers unless residency is verified.
Design
11. MUST interleave arms in rounds, in a per-round random order from the seeded RNG. Record the order. (Planned: today the order is a deterministic rotation.)
12. MUST drop warm-up repetitions by a declared rule and report the position effect.
13. MUST measure ≥12 repetitions per arm and cell. Headline claims need ≥2 independent sessions (separate boot or node).
14. MUST include an A/A arm for the reference, plus one for the arm with the lowest median when that median is below 25% of the reference's.
15. MUST keep every attempt. Classify failures as arm or infra. MUST NOT retry silently.
Telemetry (per sample, before/after)
16. MUST record cgroup cpu.stat (arm and ancestors), memory.peak (reset per sample), memory.stat anon/file, memory.events, pids, io.stat, page faults, ru_maxrss, PSS/USS checkpoints.
17. MUST record foreign CPU time on the bench CPUs, IRQ deltas, steal (iowait informational), load, runnable count, quiet-gate wait.
Statistics
18. A cell = median with BCa or order-statistic 95% CI, plus IQR, n, outlier count (|x−med| > 5·1.4826·MAD flagged, never dropped).
19. Comparisons are paired by round: ratio of medians with CI, sign-flip test, Cliff's delta. Holm over the declared confirmatory family. Everything else is exploratory.
20. "Same as Pi" needs TOST at the margins in margins.toml. Every cell shows its MDE. Inside the A/A floor = "no measurable difference".
21. Absolute values are always shown with ratios. Cross-workload summaries use the geometric mean only.
22. Every headline shows: median [CI] · IQR · A/A floor · MDE · the run notes.
Run notes and publication
23. `buffon verify` recomputes everything from raw data and lists the run notes of health.toml. A note is information. It never rejects a run.
24. Site: headlines are ci-revalidated runs on quiet dedicated hardware. Every accepted run is listed with its number of notes.
25. Closed division = default manifests and stock workloads. Open = declared changes, separate table, never ranked with Closed.
Submissions
26. A PR adds one run dir. CI checks digests, versions, coverage, no overrides of margins/health/quiet settings, recomputes the stats and the run notes, and copies the run dir to buffon-owned storage with a signed manifest.
27. Tiers: self-reported → CI-revalidated → maintainer-reproduced (ACM "Reproduced"). Every submitted run stays listed, including withdrawn ones.
28. `buffon reproduce` = reproduced iff every confirmatory ratio's CI lies inside the original's TOST margins. It shows the telemetry difference between the two hosts.
Faithfulness
29. Per-dimension scores first, overall second, weights published. N/A shown as N/A.
30. Exclusions only for structurally unpassable probes, with a reason each. Flaky probes come from a Pi-vs-Pi double run. Intentional divergences listed and counted as mismatches.
Live-model workloads (if any)
31. ≥5 trials per task, errors = 0, pass@1 ± SE and pass^k, tokens and cost, resource floor and ceiling disclosed, Harbor overlap rule for parity, trajectories published, no LLM in scoring.

### Host classes (rules 1-4)

- **Class A: dedicated.** The benchmark's CPUs are exclusive (kernel-isolated, in an exclusive cpuset partition, or the whole machine is declared dedicated by the site and nothing else was seen running on them), whole physical cores (every SMT sibling is reserved or offline), on one NUMA node, with a housekeeping CPU left for everything else, a fixed clock with turbo off, and no CPU quota in any cgroup above the benchmark. A class A result is publishable.
- **Class B: shared.** Anything else that still runs. Its results are PROVISIONAL, say why, and are never labelled quiet-dedicated.
- `buffon preflight` (flags `--cpus`, `--mock-cpus`, `--site`, `--host-claim A|B`, `--require-class A|B`, `--json`) prints the class and one line per check; `buffon run` and `buffon session` run the same preflight before measuring and record it in `raw.json` (`run.preflight`, `run.host_class`). A site's `host_claim = "A"` is a claim that the preflight checks and downgrades; `require_class` refuses to run on a lower class. A CPU quota smaller than the CPUs in use refuses the run (throttling is certain); a quota that covers them makes the run class B and leaves the per-sample throttling counter to invalidate samples.
- Kubernetes: a Guaranteed pod gets exclusive CPUs only under the static CPU manager policy and whole physical cores only with its `full-pcpus-only` option; `facts.node_class` and `node_class_reasons` of a pod run record whether the node provides both.
- The host lock is host-global (`/run/lock/buffon.lock`, else `/var/tmp`, never the per-user TMPDIR; `BUFFON_LOCK_FILE` overrides), mode 0666 so a second user is refused by it, and its holder is recorded in `run.lock_holder`.

### Host disclosure (rule 5)

Every run writes `host.json` (`buffon sysinfo` writes one by hand): CPU model, microcode, vulnerability mitigations, maximum MHz, turbo state, SMT topology of the bench CPUs, C-states, THP, ASLR, NUMA node of each CPU, IRQ steering, clocksource, the cgroup chain with every `cpu.max`, the container runtime, a hash of the boot id (two runs of one boot are one session), the bench and mock CPUs, and `host_class`. A value the machine cannot provide is null and its reason is in `unavailable`. `buffon verify <run dir>...` rejects a directory whose host.json lacks a key, leaves a null unexplained, or disagrees with raw.json about the class, whose raw.json is invalid, claims quiet-dedicated on a class B host, has no `arms.lock` digest or was run from a dirty checkout. Exit status 1 means rejected.

## 12. The developer loop (family `devloop`)

What a person pays to get an arm and start it for the first time. Each workload is N/A, with the reason, where an arm has no such step.

- `devloop/install`: clean-host install time. A fresh workspace installs the arm from the verified download cache (artifact unpack; `npm ci` from the cache for npm arms). Source-built arms are N/A here.
- `devloop/build`: build time of a source-built arm at its pinned commit with the pinned toolchain (`go build`, CGO off, trimpath). Other arms are N/A.
- `devloop/first-run`: the first print run on a fresh HOME with no first-start seed. An arm whose manifest seeds its first start (omp's unpacked natives) is measured without the seed, so the cost the other families hide shows here; `home_mb` is the size of the HOME afterwards.
- Binary and install size on disk are in the arm table of every report (`footprint`); they are properties of the install, not samples.
- Not measured yet: extension edit to reload latency, and the Piglet, AOT and fused-binary build times. They need the extension-realization arms' own builders (arms `pig-go-*`, `pig-ts-aot`); a row for them is N/A until a builder is wired in. Run these workloads inside the host's bench slot like every other, and keep each acquisition short: the clone, download and build steps of `devloop/install` and `devloop/build` are slow by nature, so run them in their own part.

## 13. Telemetry, noise and run health

- **Per-sample telemetry.** Every measured sample carries a telemetry record (docs/TELEMETRY.md): load and runnable tasks, the pinned CPUs' busy, steal, iowait, run-queue wait and clock, CFS throttling read on the sample's cgroup and every ancestor, peak memory, pids, IO bytes and page faults from the sample's cgroup, pressure, and what the quiet-host gate did. A source the machine lacks is absent, never zero.
- **Noise next to every number.** Each headline row shows the ratio with its interval, the A/A floor, the minimum detectable effect, the CV and IQR of both arms and their outlier counts. The noise report gives, per metric, the A/A gap and floor, CV, outliers and drift; it lists throttling, the gate record, flagged samples, and every sample or round left out of the statistics and why (warm-up and failures by rule; flagged rounds only with `--drop-flagged`, with the number of verdicts they would change).
- **Outliers** are values more than 5 x 1.4826 x MAD from the arm's median in a cell; they are counted and published, never dropped.
- **Throttling.** Any CFS-throttled period of a measured sample, on the arm's cgroup, an ancestor or the session, is a run note, and so is a CPU quota anywhere on the chain.
- **Run notes.** Each report lists run notes, computed from the raw data and the usual ranges in `workloads/health.toml` (docs/HEALTH.md). Each check shows its value and is `ok` or `note`. The notes inform the reader. They do not grade, reject or hide a run. They are separate from PROVISIONAL and are recomputed by `buffon verify`.
- **Time series.** Every report ships the per-round series (`rounds.csv`, plots) so drift is visible, and a change-point test on the reference arm's series (a shift is a run note).

## 14. Submissions and reproduction

- A result enters the public index only as a sealed run directory (`MANIFEST.sha256`) that `buffon verify --submission` accepts: pins equal to the lock at the runner's commit, no run made without telemetry or without its A/A copies, telemetry on every sample, and a report that matches the recomputation. Run notes, hardware class and noise gates are listed and never reject.
- CI recomputes everything from the raw data and rejects any change to an existing run directory. Tiers: self-reported, ci-revalidated, maintainer-reproduced. A headline needs quiet dedicated hardware and ci-revalidation. Withdrawn runs stay listed.
- `buffon reproduce` repeats a run's plan on another host and compares the telemetry: it says whether the reproducer's host was noisier, and which comparisons reproduced (docs/SUBMITTING.md).

## 15. Neutrality

- **Arms differ in their manifest, not in the runner.** An arm's version pin, install recipe, binary, modes, claims, capabilities, environment and config writer are fields of `arms/<arm>/arm.toml`. The runner, the workloads, the report and the statistics select behaviour from those fields and never from an arm's name. The one name they hold is the default name of the reference arm. `tests/test_docs.py` fails when another arm name appears as a string in that code.
- **The reference and every fork are configured the same way.** Pi, its forks and its ports run against the same mock, the same fixtures, the same seed and the same policy, in interleaved rounds whose order rotates. A step an arm needs and others do not (building from source, unpacking natives) is declared in its manifest, printed in the report's arms table and measured in the `devloop` family, not hidden in another family.
- **Runtime tuning is the harness's own.** Buffon pins CPUs (`sched_setaffinity` on a host, `--cpuset-cpus` in a container) and sets no runtime tuning for any arm: not GOMAXPROCS, GOGC, GOMEMLIMIT, NODE_OPTIONS, UV_THREADPOOL_SIZE or a BUN_* variable. A Go arm sizes itself by its own runtime default (PiG documents GOMAXPROCS unset, capped at min(2, the runtime default), D174), a Node arm by Node's. A variable is set only by an arm's manifest `[env]`, for every arm alike (the reference sets `NODE_COMPILE_CACHE`, a prepared cache), and the run records it in `arms[<id>].runtime_settings` with the known tuning variables it left at the default. The report prints a Runtime settings table and the site's Method page shows it. Operator variables are scrubbed, so a lane shell's GOMAXPROCS never reaches an arm.
- **Different work is labelled, not scored.** An arm's manifest may declare `[[divergence]]`: workloads (globs of workload ids), optionally metrics (globs; none means all), a `reason` and the `source` of the project's own statement (a URL or a document of this repository; each workload glob must match a registered workload). In those cells the report prints the arm's own median and `different work: not compared (<reason>)` in place of the ratio. There is no ratio, interval, test or verdict, the arm is left out of Holm's family, and the grade leaves the cell out for that arm only, in its score and in the share of the reference's cells it must cover. Every other arm is compared as before, and the reference's own divergence would leave every arm uncompared in its cells. The rule is selected by manifest fields, never by an arm's name. Today the Pi-Bolt arms declare two: a streaming tool call's arguments parsed again only once they have grown by an eighth (`overhead/print-write`), and the fullscreen TUI's scroll regions (`streaming/tui-*`). Their `$$` Markdown lexing is also declared by Pi-Bolt, but no workload streams `$$` text, so no cell is labelled for it. RPC overhead stays scored: PiG and Pi-Bolt emit the same records per turn there.
- **One scorer.** Every arm is scored by the same code, PiG included. A harness's recorded intentional divergences are listed by name and still count against its faithfulness score.
- **Metrics that favour a design are explained next to the table.** [LIMITATIONS.md](LIMITATIONS.md) lists the ones known today.
- **Numbers, not verdict words.** A report states numbers with units and spread, the ratio to the reference with its interval, and the A/A floor. A gap inside the floor is "no measurable difference". The grade and its gates are defined in GRADE.md and computed by code.

## 16. Known limitations

The limits of what a number can tell you are in [LIMITATIONS.md](LIMITATIONS.md), one section each, with what the report does about it: a mock model is not a network; mock token counts are estimates; one machine and one kernel; memory means different things, including why a macOS footprint depends on the allocator; some metrics favour a design; defaults differ; Buffon's authors also build PiG; repetitions are few; terminals, platforms and instruction counters differ; faithfulness is graded by probes Buffon wrote; and what is not measured. A report that depends on one of them says so.

## 17. Prior art

The method follows published practice and other projects' benchmarks. Each is named here for what it taught us, and none is a claim that it endorses this work.

- **Pi-Bolt's benchmark** ([repository](https://github.com/opensec-git/Pi-Bolt)). It runs fresh processes against a scripted model in interleaved round-robin order. Its scripts run unchanged as external suites (EXTERNAL.md), pinned by commit and by file digest. Its published results are imported with their provenance and checked against its own table.
- **hyperfine** ([repository](https://github.com/sharkdp/hyperfine)). It warms up, repeats each measurement and reports outliers. Buffon does the same: the first repetition of each arm is dropped as a warm-up, and the report counts outliers.
- **Georges, Buytaert and Eeckhout, "Statistically rigorous Java performance evaluation", OOPSLA 2007** ([doi](https://doi.org/10.1145/1297027.1297033)). Confidence intervals when comparing alternatives, in place of single numbers.
- **Kalibera and Jones, "Rigorous benchmarking in reasonable time", ISMM 2013** ([doi](https://doi.org/10.1145/2491894.2464160)). Repetition at more than one level, and effect sizes with their intervals.
- **Mytkowicz, Diwan, Hauswirth and Sweeney, "Producing wrong data without doing anything obviously wrong!", ASPLOS 2009** ([doi](https://doi.org/10.1145/1508244.1508275)). Measurement bias from the environment of a run. Buffon fixes and records the environment, the pins and the host.

## 18. Trust labels, noise and adaptive stopping

The strict rules of section 11 decide one thing: whether a run is **Verified**, a headline, and a row of the public results index. They do not decide whether a run is recorded. Every measurement is always recorded and always reported.

- **Gates are labels.** A calibration above its limit, a quiet-host check that gave up, a shared host, SMT siblings that are not reserved, a clock the runner cannot fix, missing instruction counters, fewer than 12 rounds and missing manifest facts do not stop a run and do not blank a report. Each becomes a reason on the run's trust badge (`buffon/trust.py`). A sample taken on a host that never went quiet is taken anyway, marked `quiet_gave_up`, and makes the run Noisy. `--require-class A` restores the old refusals.
- **The badge.** Noisy (the calibration, the reference arm against its own A/A copy, is above 5%, or the quiet-host check gave up) outranks Shared (host class B) outranks Dedicated (host class A) outranks Verified (class A, every strict rule held, reproduced: `reproduction.json` shows every comparison reproduced). A session in a slot whose calibration did not pass carries the reason `slotted` and is not Verified (section 5, "Slots on one big host"). A report that merges runs carries the worst badge of its runs. The badge sits on the report's first lines, on the grade, and on the `buffon up` summary.
- **Adaptive noise.** The run measures its own A/A noise floor (every arm has a copy in the same rounds) and every verdict is judged against it: a ratio is "faster" or "slower" only when its interval excludes 1, the difference is outside the floor and the paired sign-flip test supports it; a difference inside the floor is "no measurable difference". Where the host exposes instruction counters, instructions lead and CPU time sits beside them; otherwise CPU time leads. `raw.json` run.perf and the trust badge say which was used.
- **Adaptive stopping** (`--adaptive`, on in the quick and standard presets of `buffon up`). After each round, per workload and API, every arm is compared with the reference by the same statistics the report uses, on instructions, else CPU time, else the first scored metric. A variant stops taking rounds when every arm's answer is a win or a loss (as above), or when the whole interval lies inside the noise floor (a tight "no measurable difference"). A variant takes at least as many rounds as Holm across its compared arms allows: the smallest exact two-sided sign-flip p over n pairs is 2 / 2^n, and Holm multiplies the smallest p by the number of arms k, so the minimum is the smallest n with 2k / 2^n < 0.05. That is 6 rounds for one arm, 7 for two, 8 for four and 9 for eight. No verdict settles a variant sooner, a tight "no measurable difference" included. `--rounds` is the most a cell takes, and a cell whose cap is below its minimum runs to the cap. Measured samples stay one at a time and interleaved. Nothing is discarded: the rounds taken stay in `raw.json`, `run.adaptive.stopped` records when and why each variant stopped and the minimum it had to reach (`min_rounds`), `run.adaptive.min_rounds_by_variant` lists that minimum for every variant checked, `run.adaptive.min_rounds` is the floor for one arm, and a cell that stopped under 12 rounds cannot be Verified. The 12-round minimum applies to the Verified badge only.
- **Races.** A ladder of growing load (extensions 0/10/50/100, session size 1 prompt/1k turns/4.2M tokens) is read as a race (`buffon/race.py`, the Races section of the report): the same ladder and limits for every harness, stated once; each harness Finished (the time it crossed the last rung) or Stopped (the rung, the time and the cause: OOM, error, timeout, or cannot run), with speed, memory, reliability and resources. An OOM is a result, never a crashed run. Limits come in fixed tiers (`--memory-tier` 1, 2, 4, 8 GiB, the same for every harness) and the tier is part of a result's name. The container's own cost is measured once, as an A/A pair (the reference arm bare and in a container), and shown in the method notes.
- **The scale family is concurrent by design.** The agents of one probe of a `scale/agents-limit`, `scale/print-limit`, `scale/agents-ext10` or `scale/print-ext10` sample run at the same time, in one container (the swarm envelope: G1-G11, a memory limit, a cpuset, a pids limit, no network but the mock), so it is an exception to the serial rule of section 5: one sample at a time on the host, and nothing else running on it; the agents of that probe are concurrent by design; one probe runs at a time and never run outside the container's cgroup. The mock runs on its own CPUs outside the swarm's cpuset, as K worker processes of one socket (the serial workloads keep the one-process mock); every sample records the mock's CPU and a flag where it was saturated. Nothing guards the memory: the kernel decides, and a probe that does not complete (an OOM kill, a stall at the memory limit, a refused fork, a stage that timed out) is a failure with its cause. A sample is one round's search for the exact number of agents that complete: N doubles until the first failure and then bisects to the exact integer (`scale_resolution`, default 1), with a safety cap `swarm_max_agents` (8192) that is reported as "at least N (cap)". Every probe is recorded in the sample with its N, its outcome and its cause, and the limit of a harness is the median over its rounds with the range. A probe ends as soon as its cause is known: at the first OOM kill (the container is killed at once) or when the container has sat at its memory limit with no agent making progress for 10 s and nothing was killed (`stall`); it does not wait for the 120 s stage timeout. CPU per agent-turn and turns per second cover the same window (the turn phase), and start-up CPU is its own field. The family takes 5 measured rounds and has no A/A copy by default (an explicit `--rounds` or `--aa` wins); its noise is the spread of its rounds' limits, min to max, and a headline's 12-round minimum does not count its cells. The launcher is the relay inside the container; the host has one `docker run` client on the mock's CPUs and the runtime's daemon, which Buffon does not pin (design/SCALE.md). A publication run uses a dedicated host.
- **Grading with what there is.** `buffon grade` computes the score from the families that have data and lists what is missing (a reference manifest, a family that could not be measured, thin coverage). The grade carries the run's trust badge. `buffon grade --strict` keeps the old refusals.
